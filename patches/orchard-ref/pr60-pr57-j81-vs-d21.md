   code.** henrikklee reworked #57's J81-compatible check into a

5. **Transport pieces merge separately from logic pieces** (#60 SPI first,

## Device facts (J81 vs D21)

| | J81 (iPad Air 2) | D21 (iPhone 8 Plus) |
|---|---|---|
| Touch family | **N1** (fw 0x382, 59,288 B), family id **22** | **Z2** (fw 0x0773, ~80 KB image) |
| Match-data trap | family was 21 in the DT → discovery rejected; fix = 22 | (the 0x44 state byte = event mask, varies with fw state) |
| Sensor | 40×30, surface 14745×19657 | (d9 surface: 12153 h, x −224..6608, y −236..11960) |
| SPI controller | T7000 — **byte-wide PIO stalled after 32 B**; fix = bounded FIFO PIO in **spi-apple.c** (#60) | T8015 SPI @0x22e404000 works as-is |
| Board quirk | display-sync pinctrl absent → devm_pinctrl_get -ENODEV before the optional handling | chestnut touch-HV rail = THE hardware gate |
| Timing | geometry reads return ZERO until ~6 s after wake | settle_ms=2260 + the late WAKE (J71b order) |

## Same transport, same failure classes

- **Shared HBPP framing across N1 and Z2**: their N1 firmware upload ACKs
  `4b c1` — the same status code we found in the iOS kext's HBPP DATA path
  (prox/cal downloads, ≤1008 B chunks). The bootloader protocol is family-
  shared; the Z2's in-pocket prox calibration rides the same transport.
- **Shifted-header replies**: J81's 16-byte runtime replies sometimes put `e1`
  at byte 1 with a `00`/`01` lead and only the low checksum byte fitting —
  their fix is a J81-specific parser acceptance. Our D21 sibling: the
  data-phase header resync (Orchard 5fb60c0 port — "header in the data phase
  (N bytes pending): resynchronising"), which rescued frames mid-half-boot.
- **Runtime -EBADMSG → repeated resync** (their "choppy 10-ms contacts") =
  our checksum/EBADMSG class feeding the recovery ladder.
- **GPIO/IRQ integration**: their GPIO84 interrupt gate + pinctrl-absent
  handling vs our level-low IRQ saga (now fixed at the DTB level — see
  `diamond/payload/README-irqlevel.md`, the 0x4→0x8 correction).

## Relevance to the D21 phantom/pocket-guard investigation

- The in-pocket prox calibration is a Z2-side (iPhone-side) feature: the J81
  work never mentions prox cal, and their N1 touch works without it — consistent
  with the iPad having no pocket/prox subsystem. It does NOT refute our
  missing-PxCl theory (the Z2 fw is the one with the in-pocket subsystem);
  it DOES mean upstream has no calibration reference for it — the SysCfg
  extraction (`/dev/nvme0n3` → PxCl 144 B) remains ours to contribute.
- Their transport debugging pattern (bounded PIO + header-acceptance + family
  correction, validated by swipe report counts) is the validation template for
  our prox-cal A/B: count real contact lifecycles before/after, not idle fps.
